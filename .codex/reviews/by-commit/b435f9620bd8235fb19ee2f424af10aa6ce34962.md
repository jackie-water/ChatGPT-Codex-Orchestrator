## Independent finding [P1] — shell interpreter validation argv

The reviewer noted that if a trusted administrator EXPLICITLY allowlists an interpreter such as sh or bash in project.allowed_validation_executables, an issue step using sh with argv ['-c','echo harmless'] can be accepted, since the argument metacharacter filter does not prohibit '-c'. This can run arbitrary shell text if the trusted administrator allows an interpreter.

## Independent Chat adjudication

**NOT a deterministic unauthorized bypass of the scope/contract of P2.2a.** The P2.2a original acceptance criteria explicitly require validation steps to be *structured argv from the project's configured executable allowlist*. The system uses verified private Control event provenance, a trusted issue author and an immutable verified project configuration snapshot. With an OMITTED allowlist, only 'git' is implicitly authorized; with explicit ['git'] or [] the sh command is REJECTED; ONLY if the administrator explicitly includes 'sh' is the step accepted. These four cases were independently demonstrated in temporary isolated Mac fixtures, without executing the shell.

The existing Windows wrapper runtime/scripts/run-codex.ps1 similarly accepts executable names that the administrator has explicitly placed on the project allowlist, with string argv; the project renderer supplies a Git-only minimum. The current orchestrator-dev private configuration explicitly authorizes ['git','node','npm'], not sh/bash. Banning all interpreters or '-c' even when deliberately allowlisted would change product security policy and break compatibility with explicitly authorized project configuration; this was not part of the two user-approved deterministic fixes. It merits a separate documented security-hardening/policy decision, not another covert P2.2a revision. Explicitly trusted interpreter allowlists must be treated as granting the ability to execute code and should not be enabled casually.

No reviewer finding demonstrates that a user can bypass an ABSENT, empty or Git-only validation executable allowlist, nor that untrusted authors or other Chats can inject steps. Therefore no deterministic technical blocking issue remains against the specified P2.2a preflight scope.
